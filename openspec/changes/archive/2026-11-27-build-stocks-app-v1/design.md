# Design

## Context

The repo is empty apart from chassis, OpenSpec and `AGENTS.md`. The person's spec (Stocks App — React Native Spec, 2026-11-26) fixes the stack, the endpoint mapping, the derived values, the cache table and the project structure. This design keeps those choices and settles what that spec leaves open. For requirements, see `specs/`. For motivation, see proposal.md.

Constraints that shape the approach:
- InvestingData has no ranking, batch-quote, stats or date-range endpoints. Every quote, stat and range is derived on the device from one full-history call per ticker.
- Limits are per user plan. The test key allows 25 requests a minute and 500 a day, so the cold-start request budget matters.
- Some histories are about 5,000 bars (about 0.5 MB of JSON each, estimated), and a cold start can pull about 8 MB.

## Goals / Non-Goals

**Goals:**
- Follow the spec's layering: screens call feature hooks, hooks read through the query cache, and only the API client talks to InvestingData. Screens never see raw responses.
- Keep every derived value in pure functions, unit-tested against fixtures.
- Have each screen work offline from cache after the first successful load.
- Leave the repo with `typecheck`, `lint` and `test` scripts that can serve as its quality gate.

**Non-Goals:**
- No app store builds, EAS submit or release pipeline. Running on simulators and devices is enough for v1.
- No CI pipeline in this change. That's a separate change under the team's process doc.
- No backend or proxy: the app calls InvestingData directly with the user's key.
- No end-to-end UI automation (such as Detox or Maestro). Device checks are manual, against the acceptance list.

## Decisions

### D1. Expo development build, not Expo Go
`react-native-mmkv` isn't bundled in Expo Go, so the app runs as a development build (`expo-dev-client`) with Continuous Native Generation. `ios/` and `android/` are generated by `expo prebuild` or `expo run:*` and are gitignored, so there are still no hand-edited native projects.
*Alternative:* swap MMKV for AsyncStorage and run in Expo Go. That's simpler to start, but slower for the persisted cache, and it departs from the spec. **Decision for the person at sign-off.**

### D2. Latest stable Expo SDK, npm, strict TypeScript
Scaffold with `create-expo-app` on the then-current stable SDK, with its TypeScript template and `"strict": true`. Use npm, the default, since the repo has no package-manager history. Lint with `eslint-config-expo`. Add the scripts `typecheck` (`tsc --noEmit`), `lint` and `test` (`jest`, with the `jest-expo` preset).

### D3. Key gate in the root layout
`src/app/_layout.tsx` reads the key from secure storage once at startup (behind the splash screen) and holds it in a small React context. Expo Router's protected-route guard sends users without a key to `key.tsx`. The API client reads the key from that context, so it never touches a cache. A 401 from any request clears the in-memory key status and routes to `key.tsx` with a `rejected` reason. The stored key stays until the person replaces or removes it.
*Alternative:* re-read the keychain on every request. That's slower, and it has no benefit.

### D4. Rate limiting in one sliding-window queue
`api/queue.ts` keeps the send times of the last minute's requests and starts a new request only while the count is under the limit. The limit comes from `/v1/usage`; until it's known, the queue uses 10 a minute. Waiting jobs are ordered by priority (key check > visible rows > off-screen rows > dividends), then by arrival, and a waiting job whose request was cancelled is dropped without taking a slot. A 429 pauses the whole queue until `resets_at` (falling back to 60 s), then retries that job. The key screen's check of a newly pasted key bypasses the queue, so a 429 there fails fast with the retryable message instead of waiting on the pause.
*Alternative:* a token bucket. That allows bursts above the per-minute cap at the window edge, which the API would reject.

### D5. Retries and errors
Responses map to typed errors: `unauthorized`, `forbidden`, `notFound`, `rateLimited`, `network` and `invalidResponse`. TanStack Query retries only `network`, twice, with exponential backoff. 4xx errors never retry, and `rateLimited` is the queue's job. Screens switch on the error kind to choose the states in the specs.

### D6. Caching: query persister for small data, files for histories
TanStack Query's persister writes to MMKV, but only the `companies`, `company`, `ticker` and `dividends` queries. A dehydrate filter leaves `prices` out. Each price history is written to `documentDirectory/prices/<SYMBOL>.json` with its fetch time (`history-store.ts`). The `prices` query seeds from that file, so it renders at once, and refetches when stale, using the spec's freshness table (12 h, a 15-minute pull-to-refresh floor, no focus or interval refetch). This keeps the persisted cache small, and relaunches never refetch fresh histories.

### D7. Validation depth
zod schemas validate every response. For a price history, release builds validate the first and last 50 bars plus the array's shape, and development builds (`__DEV__`) validate every bar. Timestamps are normalized to milliseconds at the mapping step (above 1e12 is milliseconds, otherwise seconds), so derived code works only in milliseconds.

### D8. Starter validation against the index, not 15 lookups
The spec checks each starter with `GET /v1/tickers/{symbol}`. That's 15 extra calls on a cold start, on top of the index pages and 15 histories. Instead, starters are checked against the company index, and `/v1/tickers/{symbol}` is called only for a starter missing from it, with the result cached for 7 days. A 404 on a starter's price history drops it too. This keeps a cold start (about 5 index pages + 15 histories) under the test key's 25 a minute.

### D9. List ordering while loading
Rows show in the last session's volume order (cached), or in starter order on a first run, and re-sort by volume once every visible history has arrived. That avoids rows jumping on every arrival during a cold start.

### D10. Search
The company index is flattened into a list of tickers with their normalized company names (NFD, diacritics stripped, lower case) and kept in memory. A query matches a ticker prefix, or a substring of the display or legal name, 300 ms after the last keystroke. Ticker matches rank first, then name matches, alphabetically within each. Before the index is cached, a query with a letter that a ticker can't hold, or with a space, goes to the server's `search` parameter. A ticker-shaped query (like `PETR`) waits for the index.

### D11. Downsampling for 5Y and ALL
5Y and ALL are bucketed by ISO week, keeping each bucket's last close. If that's more than 500 points, the bucket widens (2, 3, … weeks) until it fits. The last point is always the latest close. This settles a gap in the source spec, where weekly closes over 20 years would be about 1,000 points, not 500.

### D12. Chart and scrubbing
The chart is a victory-native `CartesianChart` line, with its press state driving a cursor. victory-native is pinned to `~42.0.1`, whose Skia peer is `@shopify/react-native-skia` (the version Expo SDK 58 pins). victory-native 43 depends on the renamed `react-native-skia` package instead, which installs a second Skia next to Expo's, and the app crashed at launch. The scrubbed index is mapped to the JS thread only when it changes. Each change fires `Haptics.selectionAsync()` and updates the price block. Range changes animate the line between data sets. The chart's accessibility label comes from the same derive helpers (range, direction, %, start and end close).

### D13. Formatting
`shared/format.ts` wraps `Intl.NumberFormat` and `Intl.DateTimeFormat` with the device locale from `expo-localization` (a dependency the spec didn't list). Hermes ships Intl on both platforms. Currency is always BRL. Percentages are signed, and large numbers use compact notation.

### D14. Testing approach
- **Unit:** `derive.ts`, `queue.ts` (with fake timers), `schemas.ts` and `mappers.ts`, against fixtures for every endpoint in `src/features/stocks/api/__fixtures__/`.
- **Integration:** hooks and screens with React Native Testing Library, and MSW (`msw/node`) serving the fixtures. They cover the key gate, the list's states, search, and the details states.
- **Manual:** the spec's acceptance list on an iOS simulator and an Android emulator, in light and dark mode, with VoiceOver and TalkBack.
- **Native modules** (Skia, MMKV, secure store, haptics, file system) are mocked in Jest, so chart drawing is checked manually, and its data is covered by the derive tests.

### D15. Response shapes come from the OpenAPI document
The spec gives partial response shapes. Before writing schemas, confirm each endpoint's response against InvestingData's OpenAPI v1.0 document (https://api.investingdata.com.br/docs). Write the fixtures from it. Where the document and the spec disagree, follow the document and note the difference in this design.

**What the document says** (read 2026-11-26). The OpenAPI 3.0.0 document is inlined in the docs page's Scalar reference. JSON paths below are in that document. Where the document is silent, the decision is ours, and is marked *(ours)*.
- **Auth:** an `x-api-key` header only (`components.securitySchemes.apiKey`). `servers` is empty, so the base URL `https://api.investingdata.com.br` comes from the docs host.
- **`/v1/usage`** (`components.schemas.KeyUsageResponseDto`):
  - The plan is `role` (`admin` | `free` | `pro` | `business`), not `plan`. `KeyStatus.plan` maps from `role`.
  - Limits are `rate_limit.minute.{limit,used,remaining,resets_at}` and `rate_limit.day.{…}`. "Remaining today" is `rate_limit.day.remaining`.
  - `rate_limit` is nullable. When it's null, the queue keeps its default of 10 a minute.
  - The response also carries a required `history` block. We request `?range=24h` to keep it small, and the schema passes it through without validating it *(ours)*.
- **`/v1/companies`** (`CompaniesPageResponseDto`):
  - Pages come back as `{data, page, limit, total}`, with no `next`, so the page count is `ceil(total/limit)`.
  - `limit` defaults to 20 and goes up to 100, so we always send `limit=100`.
  - In `CompanyResponseDto`, `image_url`, `sector`, `subsector`, `segment` and `summary` are nullable, and so is `summary.total_shares`.
  - `search` matches "legal or display name". The document doesn't mention tickers, so ticker search stays on the device.
- **`/v1/tickers/{symbol}`** (`TickerResponseDto`): `company_id` is nullable. A ticker with no company shows its symbol in place of a name, with no logo, About section or market cap *(ours)*.
- **`/v1/tickers/{symbol}/price`:** a bare array of `TickerPriceResponseDto`, where only `timestamp` and `close` are required.
  - The document doesn't give the timestamp unit, so the 1e12 detection in D7 stays.
  - It doesn't give the sort order either, so the mapper sorts bars by ascending timestamp and drops duplicate timestamps *(ours)*.
- **`/v1/tickers/{symbol}/dividends`:** a bare array of `{ex_date: string, amount: number, date: number|null}`. `ex_date` has no declared format. We parse `YYYY-MM-DD` (or an ISO date-time), and a payout whose date can't be parsed is left out of the yield *(ours)*.
- **Errors:**
  - Every operation documents 401 ("Invalid API key") and 403 ("API key plan is not allowed"). The `{id}` and `{symbol}` operations also document 404.
  - 429 isn't documented at all, and no error has a body schema, so errors map by status code alone (D5).
  - On a 429, the queue waits for `Retry-After` or a `resets_at` (header or body) if one is present, then for the last known `rate_limit.minute.resets_at` from `/v1/usage`, and otherwise 60 s *(ours)*.
- **Not used in v1:** `/v1/tickers` (a paged list) and `/v1/tickers/{symbol}/splits`.

### D16. The real history is monthly, then daily
Measured on the person's free key, 2026-11-26, task 2.5, for 9 starters:
- **Size:** about 173 bars per ticker. That's 116 monthly bars from 2016-12-01 to July 2026, then daily bars from 2026-08-03 (about 56).
- **Recency:** the last bar is 2026-10-30, about 4 weeks before the measurement.
- **Adjustment:** no bar has `adjusted`.

The person chose to adapt the app to this data rather than to the spec's daily assumption:
- **Windows are by date, not bar count.** 52W high and low use the bars dated within 365 days of the last bar. Average volume uses the last 30 *daily* bars, where a daily bar is at most 5 days after the bar before it, so a monthly bar's volume never mixes in.
- **Ranges are date slices, as before.** 1W, 1M and 3M are fully daily. 6M and longer include monthly points before August and are drawn as they come, so scrubbing steps one bar at a time, monthly or daily.
- **No relabeling.** The session date is the last bar's date ("At close, 30 Oct"), whatever its age.
- **Less work for D6 and D11.** At this size, the history file and downsampling rarely do anything, but both stay, in case a paid plan returns full daily history.
- **What's still unknown:** whether a paid plan returns full daily, current history. The docs don't say, so the person may ask InvestingData.

### D17. Company logos
The person asked for logos during the build (2026-11-26).
- **The source is SVG.** `image_url` points to public SVGs on the API host (`content-type: image/svg+xml`, no key needed). React Native's `Image` can't draw SVG, so a shared `CompanyLogo` draws them with `expo-image`, at 36 px in list rows and 44 px in the details header.
- **Fallback:** until a logo loads, or when there's none or it fails, the same box shows the ticker's first two letters in a circle. Rows stay aligned.
- **Privacy:** the logo is hidden from screen readers, so each row stays one accessibility element. The key is never sent to the image host.

## Risks / Trade-offs

- **[Response shapes differ from the spec]** → D15: confirm them against the OpenAPI document before writing schemas. zod turns any later drift into a clear `invalidResponse`, not a wrong number.
- **[Cold-start download of about 8 MB on mobile data]** That was the spec's estimate for full daily histories. On the measured data (D16), each history is about 173 bars, so a cold start downloads well under 1 MB. → Visible-first ordering, per-file storage and the 12 h freshness rule stay, for a plan that returns more.
- **[Free-plan daily limit (500)]** → 7-day index and dividend caching, and no polling. A normal day stays far below the limit, per the spec's estimate.
- **[A development build needs Xcode or the Android SDK locally]** → D1 states this. The AsyncStorage alternative avoids it at some cost.
- **[Approximate market cap mixes share classes]** → always labelled approximate (spec).
- **[Skia and charts can't be rendered in Jest]** → chart data and labels are tested through pure functions, and drawing is checked on devices.
- **[An Expo SDK or library API change between now and the build]** → pin versions at scaffold time, and follow each library's current docs over this design where they differ.
- **[`expo-dev-launcher` 58.1.0 doesn't compile with Xcode 27.0]** Its `DevLauncherToolbar.swift` guards an iOS 27.1 API with `compiler(>=6.4)`, and Xcode 27.0 fails on it. → A `patch-package` patch raises the guard to `compiler(>=6.5)` and is applied on `postinstall`. Remove the patch once Expo ships a fixed version.
- **[`close` may not be split-adjusted]** The document doesn't say whether it is, and an `adjusted` field and a splits endpoint both exist. If it isn't, long-range charts and the 52-week stats would show jumps at splits. → Use `close`, as the spec says. Compare `close` with `adjusted` on real data during Try it and look (1.6), and raise it with the person if they differ.
  **Finding (task 2.5, 2026-11-26, real API, free key, dev build on the iOS simulator).** PETR4 returned 173 bars, with timestamps in seconds (first 1480557600 = 2016-12-01, last 1793329200 = 2026-10-30), sorted ascending (duplicates weren't checked). Bars with `adjusted` different from `close`: 0, but the real response carries no `adjusted` at all (0 of 173 bars have the field), so the comparison can't show whether `close` is split-adjusted. The other starters match (171 to 174 bars, seconds, sorted, no `adjusted`). Two things the spec didn't expect: the history is about monthly (median gap between bars is 30.0 days, so about 10 years in 173 bars, not about 2,500 daily bars), and the last bar is 2026-10-30, not the latest session. Both change what the 1W, 1M and 3M ranges and the session stats can show. Raise with the person. `B3SA3`'s `n/a` was `GET /v1/tickers/B3SA3/price` answering HTTP 404 (not found), not a bad response shape or a limit; the app showed `n/a` because the 1.5 screen treats any failure that way.

## Open Questions

- What a real 429 carries (`Retry-After`, a `resets_at` header, or a body). The document is silent, and the queue handles every case (D15). The cold-start check in 8.2 records what a live response shows.
